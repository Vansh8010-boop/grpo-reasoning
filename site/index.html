GRPO From Scratch

Group Relative Policy Optimization, the RL method behind DeepSeek-R1, written in plain PyTorch and used to teach a small open model to solve grade-school math more reliably.

How GRPO works

For each problem the model writes several answers. A program checks which are correct, and each answer is scored against the average of its own group. Above-average answers are made more likely, below-average ones less likely. No human labels and no separate value network are needed.

  • r is how much more (or less) likely the updated model makes each word of an answer than the model that wrote it.
  • Clipping at 1 ± ε (0.2) stops one batch from moving the model too far.
  • The KL term (β = 0.04) pulls the model back toward the original, which here is the same weights with the LoRA adapter switched off.
  • Every term is computed only over the answer's tokens, never the prompt or padding: the most common silent bug in GRPO code, and the one the tests check hardest.

Ablations

Six one-change experiments on the 0.5B model, 250 steps each, scored on GSM8K test at the final step. Every variant beat the base model; none was significantly different from the baseline run.

Group size
With 4 answers per problem, 42% of groups were all right or all wrong and taught nothing (26% at 8, 15% at 16). Eight is a sound default.
KL penalty
Removing it let the model drift 6× further and write 13% shorter answers, with the same accuracy.
Format reward
Not needed on GSM8K: the model learned to box its answers anyway, because correct answers were already mostly boxed.
Advantage normalization
Without dividing by the group's spread, updates are about half as large; it behaved like a lower learning rate.
Learning rate
3e-5 collapsed into garbage tokens and ended with the smallest gain.

Reward hacking hunt

All 1,297 high-reward training answers were screened for answers that earn reward without honest reasoning, and every flagged one was read. Two were questionable. The exact-answer reward is hard to game on GSM8K.

What didn't work

The 1.5B model did not improve on the test set

Validation rose from 83.4% to 88.4% (p = 0.001), yet GSM8K test stayed at 75.7% vs 75.8%: 87 problems fixed, 88 broken. Near-duplicate problems were ruled out. At equal difficulty the base model is about 8 points better on GSM8K's training split than on its test split, which points to contamination: the model has likely seen the training split before, so improving on it did not transfer. A validation set drawn from that split was an optimistic guide.

Late-training collapse

Both the 0.5B run at lr 3e-5 and the 1.5B run after about 330 steps started producing garbage tokens in sampled answers, while greedy validation looked fine. The garbled answers got near-zero reward, so this was not reward hacking; the cause is an open optimization question. A garbage-rate metric logged every step caught it immediately.

Compute

Everything ran on Kaggle's free T4 GPUs (30 hours a week, two sessions at a time), which shaped the design: LoRA, a 250-step budget for ablations, vLLM generation on the second GPU, and resuming runs across sessions.

Reproduce it

pip install -r requirements.txt            # plus torch for your CUDA version
python -m pytest -q tests/                 # parser, rewards, advantages, loss
python -m eval.harness --model Qwen/Qwen2.5-0.5B-Instruct --dtype float16 --out results/base-0.5b
python -m grpo.train --config configs/grpo-0.5b.yaml    # 250 steps, about 6.5 h on one T4
python -m eval.harness --model Qwen/Qwen2.5-0.5B-Instruct --dtype float16 \
    --adapter checkpoints/grpo-0.5b/ckpt-0250 --out results/grpo-0.5b

Every experiment has a config in configs/; every number on this page is generated from results/ by site/build_data.py.
